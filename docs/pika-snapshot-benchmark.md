# Pika H3 Flex 快照与预热全因素实测（2026-11-25）

## 结论

在本轮同一 768p T2VA 工作负载、两次独立冷启动及一次热态请求中，**A（GPU Snapshot + 480p 预热）是延迟最优方案，B（关闭快照、保留预热）是次优方案**。保留正式部署的 A 配置，不修改生成精度、步数、缩容窗口或常驻容器数。B 适用于频繁发布、预计只用一次容器生命周期且快照难以复用的场景；并不意味着 B 在任意节点的首次部署都更快。

## 实验设计与证据

- PC2 Modal profile `zhangchenzer`，基线提交 `d2e57bf867d1bedf3fde829be439fc96fb0573b1`，四个隔离 App，共用同一权重缓存指纹 `b9bd0bc45e43db106020dcd269de7eafbc2e12d6b7f215890aa14d9a5b76f85b`。正式 App `002-pika-h3-flex` 不参与部署或停止。
- RTX PRO 6000 ×1，4 CPU、48 GiB 请求内存，单容器串行，min=0、max=1，缩容窗口 60 s；SGLang 固定版本 1173264b58，memory performance mode，保持现有 layerwise offload、原生六步采样及 TORCHINDUCTOR_COMPILE_THREADS=1。
- 四组唯一实验因素是 `memory_snapshot`（gpu/off）及启动预热。预热组显式 `--warmup-mode server --warmup-resolutions 864x480`；无预热组移除画布参数，显式 `--warmup-mode off`，避免上游自动切回预热。预热实际 124 帧、2/6 步；不是降低业务推理画质。
- 同一 `tasks/004-pika-video-demo.json` 首条 prompt，seed=1101，768p/16:9/5s。直接通过正式 Backend.submit + FunctionCall.get 提交首条业务；首轮第二条热态请求后，轮询确认旧容器退出，再提交第二轮首条任务。两组快照均在第二次启动命中，故无需第三轮。四组并行会带来宿主与存储竞争，不是同一物理节点上的严格配对实验。

## 费用与策略边界

实际 workspace 单价：RTX PRO 6000 $3.03/GPU-h、CPU $0.0473/core-h、内存 $0.008/GiB-h。按 4 CPU、48 GiB 请求量计算资源费率 $3.6032/h；实际超请求的 CPU/内存用量可能增加费用。GPU 初始化、捕获、恢复、推理及空闲分配均有成本。采用平台分钟桶的分配量积分，而非 SDK 等待时间计算 GPU 秒；CPU/内存取每桶请求值与平均实际使用量的较大者进行近似，不能冒充精确账单。完整小时账单仅取得 04:00–05:00 UTC 部分实验（四组合计约 $0.887），05:00–06:00 尚未完整，不能声称已核准最终实扣费用。详见 [Modal pricing](https://modal.com/pricing)、[billing report](https://modal.com/docs/reference/cli/billing) 与 [memory snapshots](https://modal.com/docs/guide/memory-snapshots)。

用同等基础初始化假设做示意：A 捕获额外约 34 s、B 第二轮排队至方法开始 162.70 s、A 真恢复 34.14 s；若每次未命中多付约 34 s、每次命中节省约 129 s，则期望时间持平命中率约 21%。这不是同节点实测阈值，宿主、快照存储及排队波动都可能改变结果。对只有一次初始化的批次不能假设快照必然降低成本。

下一步若进一步优化，优先以 A 为对照测试合法的更短 480p 预热时长（例如 4 s），保持真实生成任务、精度、画布和六步采样不变；分别测真实首条延迟、恢复命中、画面和音频。不要把未测试的预热参数当成已验证最优。稳定大批量作业优先一次启动连续生成，不应为了快照复用主动反复缩容。
